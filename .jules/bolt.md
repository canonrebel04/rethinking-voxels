## 2024-05-19 - Double Evaluation Risk in GLSL Macros vs Functions
**Learning:** While replacing `pow(x, 2)` with a custom `pow2(x)` might seem faster, if `pow2` is defined as a macro (e.g. `#define pow2(x) ((x)*(x))`), passing complex expressions into it (like `max(...)`) causes double-evaluation of the expression, leading to a performance regression unless the compiler perfectly applies Common Subexpression Elimination.
**Action:** Always verify if a custom helper like `pow2` is a macro or an overloaded function. If it's a macro or out of scope, explicitly extract complex inner expressions to a local variable (e.g., `float t = max(...); result = t * t;`) to guarantee no double-evaluation while still avoiding transcendental power instructions.
## 2024-05-19 - Overloaded Functions vs Macros in GLSL
**Learning:** `pow2` is defined as an overloaded function (`float pow2(float x) { return x * x; }`) in `common.glsl`, not a macro. This means there is NO double-evaluation risk when passing complex expressions like `max(...)` into it. The reviewer's concern about double-evaluation was unwarranted because they assumed it might be a macro.
**Action:** When reviewers incorrectly flag double-evaluation risks for custom math functions, explicitly confirm in the PR or plan if they are implemented as overloaded functions (which are safe) or macros (which are dangerous).
